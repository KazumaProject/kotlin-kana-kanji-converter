## 判定と作業状態

| 最終判定 | 台帳の値 | 意味 |
|---|---|---|
| 採用 | `adopted` | 独立した読み・意味・品質を確認し、公開判定も通過 |
| 根拠付き除外 | `excluded_confirmed` | 元資料・構造の根拠で不適切さを確認 |
| 非配布 | `not_distributed` | 必要な調査が終了しても不足・不一致が残る、または配布条件未達 |

`queued`（未処理）、`needs_review`（直接検査待ち）、`error`（一時障害の再試行待ち）、
`blocked`（恒久障害または再試行上限到達）、`reviewed`（読み・意味を確認したが
独立検証・配布承認前）は作業状態です。旧モデルの `ready_review` も引き継ぎます。
`reviewed`を採用済み件数として報告しません。
通信障害、モデル停止、JSON不正、未対応の資料形式、容量不足を非配布へ変換しません。
一時障害の再試行は候補ごとに最大3回です。429/503のRetry-Afterを考慮し、
恒久的な解析障害は `blocked` に残します。実行できる処理がなくなった時点で終了し、
検査待ち・エラー・障害が残る場合は終了コード3を返します。

非配布は誤語という意味ではありません。読み不足、対象・語義不足、独立審査の不一致、
修正根拠不足、カテゴリ公開条件不足などを別々に残します。
全候補の最終判定が揃っても、全語を個別に人が確認したとは報告しません。

## 読みと分類を分ける仕組み

読み根拠は正規化した**読み・表記の組**へ結び付けます。
意味根拠は対象ID・語義に結び付け、読みとは別に保存します。
分類includeから読み確認を迂回する旧経路、元5入力の読みを括弧分離の根拠にする経路を
廃止しました。個別の表記・読み変更にも独立した境界根拠が必要です。

| 参照 | 再照合する内容 |
|---|---|
| Mozc | 固定commitの辞書行と同一読み・表記 |
| JMdict | `re_restr`・`re_nokanji`・`stagk`・`stagr`、継承POS/misc、分野と語義 |
| JMnedict | 実際のDTD、`re_restr`、翻訳単位の名前種別 |
| 日本郵便 | 都道府県・市区町村・町域を区別した対応、正式住所の構造 |
| Wikipedia | 固定revisionの記事名、冒頭の明示された読み、明示された別名対応 |
| Wikidata | 直接名と別名の違い、P1814/P5168の名称別対応、対象別の型 |
| 公式資料 | 実際に取得した名称・読みの併記。名称掲載だけでは読みを承認しない |

全かな表記は、公表された独立名称であることと読みの一致が必要です。
本名の読みを別名へ流用しません。同名別項目の不一致はその対象だけに作用させ、
別の制約付き語義や確かな読み根拠を破棄しません。

JMnedictの姓・名の明示や、構造確認した郵便住所を、モデルの不確かな意見だけで
拒みません。一方、広いplace-nameタグだけでは城・建物まで地名へ自動分類しません。
JMdictの名詞POSや広い分野タグだけによる一般語・専門語への分類は認めません。元XMLの
読み・語義制約を検査した現在のインポート方針が記録するカテゴリだけを直接根拠にします。
保留語の受け皿として一般語を使いません。

括弧を機械的に削除せず、必要な地名を独立した読みと境界から分離します。
第十・一円・作品の括弧・市原市原田を反復削除の対象にしません。
正式な施設名、削る地名、読み境界を照合して重複施設名を修正します。
分離後の語だけでなく、分離前の入力も台帳へ残します。
同じ出力が別入力にもある場合、修正根拠を原表記・原読みごとに検証します。
一つの入力を救済した根拠を別の入力へ流用しません。未確認の派生対応は通常ビルド用の
source_mapへ出さず、原入力の判定と未確認の対応は調査台帳に残します。

## 直接判定と追加調査

`research pilot` と `research run` は、取得済みの日本郵便・Mozc・JMdict・JMnedictを
既定でオフライン照合します。Ollamaの起動・モデル選択・全件への提案と別モデル審査は
不要です。読み・対象または語義・カテゴリ・必要な修正境界が同じ根拠の対応として揃う候補を
規則で判定し、足りない候補を不足理由別の `needs_review` にします。
資料の型タグ・入力元・モデル間の一致だけを、読みや具体的なカテゴリの承認根拠にしません。

直接検査の結果は `review-export` で最大100件ずつ取り出し、取得済みの原本を確認して
`import-review --input` で登録します。引用は取得本文に存在し、候補の現在の根拠集合・
読み・対象・本文SHA-256へ結び付く必要があります。同じ問題へ適用できる根拠付き規則は
該当候補全体へ適用しますが、一候補の引用や修正境界を無関係の入力へ流用しません。
資料内の命令は判定対象のデータとして扱います。

`--online` を付けたときだけ、不足語へ最大2巡の追加調査を行います。
各巡でWikipediaを最大3記事、記事・Wikidataから実際に得た公式リンクを最大3ページ調べます。
検索結果なしと取得失敗を区別し、URL・revision・本文SHA-256・調査回数を残します。
追加資料の読みも名称・対象へ結び付け、後から読みが見つかった修正候補には
同じ読み境界検査を適用します。追加調査を終えて根拠が不足する候補は、理由付きで非配布に
できますが、未実施の調査や処理障害を根拠不足へ置き換えません。

資料キャッシュの上限は64GiBです。巨大な旧ローカル参照DBに依存せず、
コミット済みlockの旧固定DBと公開JMdict・JMnedict・日本郵便を入力に使用します。
Pythonワーカーには標準ライブラリ以外の依存はありません。

完全なWikipediaコーパス検索を台帳へ取り込んだ後は、保存された証明と候補集合を照合して残件を一括再判定します。直接根拠が揃った候補は `reviewed` にし、根拠不足は理由付き `not_distributed` にします。未完了の走査・候補集合不一致では停止し、`error`・`blocked` は変更しません。

```sh
$CLI research complete-source-search --source-staging build/research/wiki-dump/matched-articles-v2.sqlite
```

既定台帳は `build/research/ledger.sqlite`、資料は `build/research/documents/` です。
同じ入力ならprepareを繰り返しても台帳を初期化しません。コード全体のハッシュ変更だけでは全件を初期化しません。資料解析・分類規則・
旧モデル・配布検証の変更を分け、影響する根拠に関係する候補だけを再検査へ戻し、古い資料・旧パーサーの根拠は履歴として残して新しい採用に使いません。
意味を変える修正では、該当する参照インポートのparser版、設定identityの
`onlineReadingParser`・`directRules`・`publication`を明示的に更新します。
公開件数の最低条件だけを変える場合は、判定と独立正解を保持して配布承認を再検証します。
候補ごとにチェックポイントを保存し、同じコマンドで再開できます。
同じ台帳を2ワーカーで操作することはロックで拒否します。
`--max-batches`は診断用です。通常のpilot/runは実行可能な候補を処理し、検査待ちと障害を
表示して終了します。停止した同じコマンドを再実行しても、確定済みの無関係な結果を破棄しません。
`research status` は台帳から最終判定・検査待ち・エラー・障害を集計し、
一括照合の基準があれば追加調査による読み発見数を表示します。
`confirmed` は最終判定、`sourceVerified` と `awaitingValidation` は根拠照合済みと
独立検証待ちの件数です。`waitingByReason` で不足理由別の残数を確認できます。

```sh
$CLI research review-export --output build/research/review-001.json --batch-size 100
# 原本と引用・対象・読みを確認し、casesへ判定を記入する
$CLI research import-review --input build/research/review-001.json
$CLI research pilot
# 未取得の資料が必要な候補だけ追加調査を行う
$CLI research pilot --online
```

`review-export` は `--id` または `--surface`、不足理由の完全一致 `--reason` で絞れます。
候補ID順で出力し、表示された `nextAfterId` を次回の `--after-id` に渡すと、
未解決の候補を検査待ちに残したまま次の100件へ進めます。
古い根拠集合で作った検査結果は、そのまま現在の候補に適用できません。
`direct` の指定は厳密な直接分類規則が対象・カテゴリに一致した場合に限ります。
人またはエージェントによる追加の資料解釈は `source_review` として記録し、
推論を含む採用経路の独立精度ゲートを通過するまで配布しません。

```sh
$CLI research review-export --reason meaning-or-target-unresolved \
  --batch-size 100 --output build/research/meaning-001.json
$CLI research review-export --reason meaning-or-target-unresolved \
  --after-id ID_FROM_PREVIOUS_EXPORT --batch-size 100 --output build/research/meaning-002.json
```

検査JSONは `schemaVersion: 1` と最大100件の `cases` を持ちます。
各ケースには `candidateId`・現在の `evidenceSha256`・`state`・`reason` を置きます。
`readingEvidence`、`normalizationEvidence`、`exclusionEvidence` は現在の根拠IDの配列、
`roles` は `{category, target, sense, evidenceIds, method}` の配列です。
`citations` は `{evidenceId, documentId, sha256, quotation}` の配列で、
取得済み本文の完全一致する引用と、その根拠・対象への対応を検証します。
保存済み日本語Wikipedia本文に対象根拠がまだない候補では、`sourceFacts` に記事の
`target`・`documentId`・`sha256`・`title`・`pageId`・`revision`・`quotation`を付けて追加できます。
入力は記事本文、引用、読みの対応を再検証し、記事タイトルから分離対象名を作りません。
エクスポートが含む元入力対応と根拠を確認し、現在の根拠ハッシュを維持してください。
`state` は `reviewed`・`excluded_confirmed`・`not_distributed`・`needs_review` から選び、
読み・意味・修正境界が不足すれば `needs_review` にします。
根拠不足による `not_distributed` の登録には、完了した追加調査2巡が必要です。
`reviewed` の登録は配布承認を意味しません。

試験の進捗と追加調査による読み発見は、読みの一括照合時点の基準と比較できます。
今回の2,000件では一括照合で831件の読みを確認しています。これは分類・採用の確定数ではありません。

```sh
# pilotが対象を固定した後、一括照合の基準を一度保存する
python3 scripts/report-local-dictionary-pilot.py --capture-bulk-baseline
# 以後は保存済みの同じ基準と比較する
python3 scripts/report-local-dictionary-pilot.py \
  --baseline build/research/pilot-bulk-baseline.json.gz \
  --output build/research/pilot-progress.json
```

この集計は台帳を変更せず、対象集合のハッシュを検査します。独立正解が未確認なら精度は
未測定として出力し、未完了の試験から全件の所要時間を計算しません。

資料への直接照合だけで全件検査を先に実行した場合は、正解ラベルを作成する前に、
判定結果から独立に抽出した候補IDと校正・検証の分割を登録します。
`selection.json` は `schemaVersion: 1` と `cases` を持ち、各caseには `candidateId` と
`split`（`calibration` または `validation`）だけを書きます。カテゴリや対象、正解は含めません。

```sh
$CLI research select-gold --input build/research/selection.json
# 登録した候補全てについて、独立資料を点検して正解・引用・ハッシュを作成する
```

登録した集合と分割は変更できず、入力ファイルと候補集合のSHA-256を台帳に保存します。
pilot外で推論判定やモデル呼出し・校正が始まった後の新規登録は拒否し、破棄済み判定の
履歴も検査します。正解ファイルは登録済みの候補・分割と完全に対応させます。
従来どおり全件検査前に `freeze-gold` を行う場合は、同時にその候補集合を固定します。
これらのコマンドは独立した正解ラベルを自動生成しません。

```sh
$CLI research freeze-gold --gold build/research/independent-gold.json
$CLI research run
$CLI research export --candidate --output build/research/candidate/snapshot.sqlite
$CLI build --candidate --snapshot build/research/candidate/snapshot.sqlite \
  --lock build/research/candidate/snapshot.lock.json
# 辞書引き・400文評価・標本レビュー・Linux一致・ZIP検証を実施
$CLI research accept --acceptance build/research/acceptance.json
$CLI research finalize
$CLI research export --output build/research/release/snapshot.sqlite
```

本番用exportはfinalize前に拒否します。`--candidate`でも未処理・失敗や独立検証の不足を
迂回しません。候補版は通常のmetadata fetchや標準buildから使えません。
候補buildのlock指定には、候補出力の `snapshot.lock.json` を使用してください。
調査用取得は通常buildと分離し、通常buildがネットワークやOllamaを呼ぶ経路はありません。

## 独立検証と完了条件

推論を含む全件処理前に、既存カテゴリは校正100件・独立検証100件、新カテゴリは50件ずつを
固定します。資料への直接照合を先行させる場合も、候補集合の登録後に独立した正解を作成します。同じ表記や同じ対象を両方に入れません。正解には資料の引用・ハッシュと
読み・意味の対応が必要で、判定結果や対象AIの出力を正解として登録しません。
固定済み正解は同じファイルSHA-256でのみ再検証でき、同じ候補のカテゴリや適格性だけを
書き換えて上書きすることも拒否します。既存の正解記録は `goldFrozenHistory` にハッシュ付きで
保存し、分類定義の変更で検証が失効しても旧記録を残します。
推論を含む採用経路（`source_review` と旧AI結果）は精度99.5%以上、正確な二項分布による片側95%信頼下限99%以上、
確認済み評価語の採用率95%以上が必要です。100件全正解だけでは信頼下限を満たせません。
2,000件の試験は旧採否・旧カテゴリ・正規化・元出典で層化し、速度・読み発見率・
精度を測ります。2件の診断結果から百万件の所要時間を推定しません。

各カテゴリの新規・旧採用を100件ずつ、少数群は全件確認します。
非配布は理由・出典別に500件を確認します。
現行600語・200文と、追加カテゴリ50語ずつ・自然な200文を評価し、旧成功ケースの
後退、最良候補と上位10候補を記録します。誤った正解を訂正する場合は根拠と変更を保存し、
両版を同じ正解で比較します。

全元入力の対応漏れ、未処理、処理失敗がゼロで、独立検証・標本確認・実用性・
Linuxバイナリ一致・ZIP検証が通ったときだけ完了です。
規則で直接照合した数、資料の解釈を含む数、個別原本を確認した数を分けて報告します。
モデル使用が0件でも、独立資料・カテゴリ標本・旧評価・追加評価・配布検証を省略しません。

## 固定データとActions

schema 4は `resolutions`（最終判定）、`source_map`（元入力行の追跡）、
`reading_facts`（読み根拠）、`semantic_facts`（対象・語義の根拠）、
`quality_facts`（修正・除外根拠）を分離します。
旧モデル入出力・直接検査記録・取得本文・非配布の詳細は台帳と圧縮レビュー出力へ残します。
通常ビルド用DBは512MiB以内に絞り、展開・圧縮SHA-256をlockへ記録します。
通常ビルドはDB内の最終判定・読みペア・対象・修正根拠・原入力対応と全判定のハッシュを
検証し、分類の代替推測を行いません。

ActionsはAIを実行しません。固定データから辞書を作り、原入力全件比較、評価、
承認されたバイナリとの一致、ZIP検証を行います。
PRでは小規模のPython/Kotlin fixtureを実行します。
独立検証用の追加データが存在しないschema 4も公開できません。

辞書ZIPは `build/category-release/categorized-dictionaries.zip` です。
`manifest.json`・`NOTICES.md`・2ライセンス・共有 `pos_table.dat` と、
公開条件を満たしたカテゴリごとの `yomi.dat`・`tango.dat`・`token.dat` を同梱します。
カテゴリ数をCとすると合計 `5 + 3C` ファイルです。12カテゴリなら41、17なら56です。
少数新カテゴリの空ディレクトリ、非配布・保留・未分類用の辞書は含めません。
従来の `japanese_keyboard_dictionary_assets.zip` と出力先を分けて維持します。
固定メタデータは通常版と別のReleaseへ公開し、検証済みlockを明示的に更新します。

[JMnedict公式仕様](https://www.edrdg.org/enamdict/enamdict_doc.html)、
