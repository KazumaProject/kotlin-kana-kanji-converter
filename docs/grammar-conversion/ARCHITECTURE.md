# 文法セッションの設計

`KanaKanjiEngine.grammar(metadata)` は、既存の辞書から生成した文法メタデータと、ロード済み辞書・連接行列を使う。追加辞書のノードも明示条件の評価前に同じラティスへ合流する。

1. `generateGrammarMetadata` は既存の Mozc 解析器と `-PmozcIdDefFile` を使用する。新しい companion ファイル KKG1 に連接行列と POS ID 配列の SHA-256、ID 件数、ID 順の定義ラベルを記録する。実行時に資産ハッシュ、行列次元、フォーマットを検証する。
2. `CompiledGrammar` は UTF-16 制約を検証し、ID に対するマスクへ変換する。スパン内を部分的に覆うノードと境界を横断するノードに除外理由を付ける。
3. `GrammarSearch` は `(ノード, 左条件まで成立した解釈集合)` の DAG を構築する。右条件はこの同じ集合に対して検査する。こうして、左右で別々の解釈を使う抜け道を防ぐ。
4. 逆順 Viterbi が `最小残余 = min(連接 + 単語 + 文法ペナルティ + 次状態の残余)` を計算する。A* は到達可能な状態だけを展開し、`累積 + 残余` の小さい順に完了経路を取り出す。どちらも Long 単位。EOS への連接費用を含める。
5. 経路列挙後に既存規則と同じ N-gram / v4 / v5 照合と候補上限を適用する。後続の v5 一致は合法な同表記経路からのみ成立する。構文制約が適用された後の経路だけが順位付けに入る。
6. `containsCandidate` は同じ DAG 上に表記中の一致位置を伝播させ、N-best の上限と独立に表記の存在を検証する。

通常変換は従来の Viterbi と A* を呼ぶ。文法付きの評価を選ぶと、形容動詞連体形の接続条件に違反した辺に、呼び出し側が指定した非負のペナルティを加える。明示制約はペナルティとは別に硬い条件として適用できる。

RAM 上では文脈 ID の配列、役割のビットセット、ノードごとの解釈集合を使う。ローカルな前後関係を超える文法には文法状態の追加が必要となる。
